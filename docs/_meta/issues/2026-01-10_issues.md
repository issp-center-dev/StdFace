## Issue 3: No include/ directory - headers in src/

**Pain point**: claude.md Section 1 states "Public API is defined by public headers in `include/`" but this project has no `include/` directory. All headers are in `src/`.

**Root cause**: Project structure differs from typical C project layout. This is a design choice, not an error.

**Fix**: Document the actual location (`src/`) in header_map.yaml. Add explicit note that headers are in `src/`, not `include/`.

**Prevention rule**: Always verify assumed directory structures before documenting. Use Serena `find_file` to locate headers.

**Affected files**: `docs/_meta/header_map.yaml` (documented), claude.md (assumption noted)

## Issue 4: Conditional compilation affects API visibility

**Pain point**: `export_wannier90.h` functions (`ExportGeometry`, `ExportInteraction`) are only available when `_HWAVE` is defined. This conditional API is not immediately obvious.

**Root cause**: Functions are wrapped in `#if defined(_HWAVE)` preprocessor block.

**Fix**: Document the conditional in header_map.yaml with `conditional: "_HWAVE"` field.

**Prevention rule**: Always check for preprocessor conditionals when extracting API. Use Serena's symbol tools which may miss conditionally-compiled code.

**Affected files**: `src/export_wannier90.h`, `docs/_meta/header_map.yaml`

# Phase 2 (Developer Architecture Documentation)

## Issue 5: macOS resource fork files causing Sphinx build failure

**Pain point**: Sphinx build failed with `UnicodeDecodeError` when trying to read `._*` files (macOS resource forks) as RST.

**Root cause**: macOS creates `._*` binary files as resource forks. These were not excluded from Sphinx processing.

**Fix**:
1. Deleted all `._*` files from `docs/` directory
2. Updated `docs/conf.py` to exclude patterns: `['_meta', '._*', '_build']`
3. Removed non-existent `_static` from `html_static_path`

**Prevention rule**: Always configure `exclude_patterns` in `conf.py` for non-RST directories and OS-specific files.

**Status**: Fixed

---

## Issue 6: RST table alignment errors

**Pain point**: Sphinx reported "Malformed table" errors in `overview.rst` and inline literal warnings in `execution_flow.rst`.

**Root cause**: Grid table columns were too narrow for content with backticks (e.g., `StdFace_Orthorhombic`), causing right border misalignment.

**Fix**: Widened the Function column in affected tables to accommodate longest entries.

**Affected files**:
- `docs/dev/architecture/overview.rst` (lattice table)
- `docs/dev/architecture/execution_flow.rst` (parsing functions table)

**Prevention rule**: When creating RST grid tables with inline literals, ensure column width exceeds content length including backticks.

**Status**: Fixed

# Phase 3 (Developer API Documentation)

## Issue 8: Sphinx C domain param syntax with grouped parameters

**Pain point**: Using `:param site1, spin1:` syntax caused Sphinx C domain parsing errors.

**Root cause**: Sphinx's C domain requires one `:param` directive per parameter; comma-separated parameter names are not supported.

**Fix**: Split grouped parameters into individual `:param` directives.

**Example**:
```rst
# Before (error)
:param site1, spin1: First site and spin

# After (correct)
:param site1: First site index
:param spin1: First spin index
```

**Affected files**: `docs/dev/api/StdFace_ModelUtil.rst`

**Prevention rule**: Always use one `:param` directive per function parameter in Sphinx C domain.

**Status**: Fixed

---

## Issue 9: Sphinx c:member directive with multiple declarations

**Pain point**: Using `.. c:member:: double V, Vp, Vpp` caused C declaration parsing errors.

**Root cause**: Sphinx's C domain expects each `c:member` directive to declare exactly one member.

**Fix**: Changed from `.. c:member::` directives to plain text documentation format using inline code markup.

**Affected files**: `docs/dev/api/StdFace_vals.rst`

**Prevention rule**: For structures with many fields, use plain text documentation format rather than individual `c:member` directives.

**Status**: Fixed

---
